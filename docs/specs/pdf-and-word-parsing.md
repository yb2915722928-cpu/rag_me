# PDF 与 Word 解析为保留关系及来源的 Markdown 正文

## Problem Statement

用户需要把 PDF 与 Word 解析笔记中的路径选择和核验方法落实到自己的 RAG 项目，并能通过实际输入与输出理解对应代码。当前 PDF 与 Word 解析模块只有目录骨架，尚无可运行的解析入口、正文转换、页或正文块来源关联，也没有相应的行为测试。

仅得到非空文字不足以支撑后续检索：数字 PDF 可能丢失标题或拼错阅读顺序；扫描页可能只得到图片引用，或者 OCR 漏掉否定词、数字、单位；表格可能保留全部文字却丢失设备与周期的对应关系；DOCX 也可能在转换时把表格移到所有段落之后。来源位置若不准确，即使文字正确也无法可靠回查。

## Solution

在 PDF 与 Word 解析子模块提供可独立使用的公开解析入口，处理调用方已取得的 PDF 和 DOCX，返回整篇 Markdown 正文、与正文对应的来源信息，以及独立的警告或失败原因。

PDF 按页利用可用文本层，扫描页实际执行图像识字；DOCX 利用原生标题、段落和表格结构，保留正文阅读顺序。以正文、阅读顺序、标题、表格对应关系、来源定位五个维度核验代表样本，作为交给后续处理的依据。

## User Stories

1. As a 知识库开发者, I want 解析本地 PDF 文件, so that 已取得的资料能够进入统一正文处理流程。
2. As a 知识库开发者, I want 解析本地 DOCX 文件, so that 能够利用原生文档结构提取知识。
3. As a 调用方, I want 使用已经取得的文件字节及明确的格式和来源调用解析入口, so that 不必为了转换重新获取原文件。
4. As a 调用方, I want 通过本模块的公开入口完成解析, so that 不必依赖尚未完成的上传 API 或总路由。
5. As a 内容核验者, I want 取得整篇 Markdown 正文, so that 可以对照原文检查内容并交给后续处理。
6. As a 下游模块开发者, I want 正文、来源、警告和失败原因分别表达, so that 诊断信息不会作为知识正文继续处理。
7. As a 知识库开发者, I want 数字 PDF 优先利用质量可用的文本层, so that 减少不必要的图像识字开销与识别误差。
8. As a 知识库开发者, I want 同一 PDF 的不同页面可以采用不同提取路径, so that 数字页与扫描页能够在同一文档内处理。
9. As a 内容核验者, I want 文本层存在时仍能检查正文质量, so that 不会把可提取文字直接等同于完整可靠的内容。
10. As a 内容核验者, I want 检查数字 PDF 的标题文字及章节归属, so that 局部标题损失能够被发现。
11. As a 内容核验者, I want 检查数字 PDF 的阅读顺序, so that 双栏或区域内容不会因错误拼接产生错误关系。
12. As a 知识库开发者, I want 扫描页经过实际渲染与图像识字, so that 图片中的目标文字有机会成为可处理的正文。
13. As a 内容核验者, I want 区分图片引用、识字结果和表格结构恢复结果, so that 不会把其中一步冒充整条解析路径完成。
14. As a 调用方, I want OCR 不可用或执行失败时取得明确原因及相关页面, so that 能够定位缺失的处理能力。
15. As a 内容核验者, I want 用原文核对 OCR 中的否定词, so that 不会把“不得带电维护”变成相反规则。
16. As a 内容核验者, I want 核对 OCR 中的数字和单位, so that 维护周期等关键信息不会被误读。
17. As a 内容核验者, I want 对照扫描表格检查表头、行列及单元格归属, so that 识出全部词仍丢失对应关系的问题能够被发现。
18. As a 内容核验者, I want 知道 OCR 返回的位置属于哪种坐标空间, so that 不会把输入图片的像素位置误用为原 PDF 坐标。
19. As a 知识库开发者, I want 按 DOCX 正文中的原始顺序读取结构, so that 表格仍位于相关的前后说明之间。
20. As a 内容核验者, I want DOCX 的标题层级保留在转换结果中, so that 能够识别内容属于哪个章节。
21. As a 内容核验者, I want DOCX 的段落正文完整保留, so that 维护前后的说明可以共同解释表格。
22. As a 内容核验者, I want 普通 DOCX 表格保留表头与单元格对应关系, so that 每个值仍可解释其对象和属性。
23. As a 知识库使用者, I want 在转换结果中区分“泵—每月”和“阀门—每季度”, so that 固定问题具有明确的关系证据。
24. As a 知识库开发者, I want 在已经核对同版本且内容完整的条件下优先利用 DOCX 原生结构, so that 减少从 PDF 视觉布局猜测关系的成本。
25. As a 内容核验者, I want 每个解析结果保留原文档标识, so that 可以确认正文来自哪份输入。
26. As a 内容核验者, I want PDF 内容关联其实际 PDF 页序, so that 可以回到对应页面检查。
27. As a 内容核验者, I want 区分 PDF 页序与印刷页码, so that 引用不会混淆两个不同的位置概念。
28. As a 内容核验者, I want DOCX 内容保留章节和正文块位置, so that 在没有可靠渲染页码时仍能定位出处。
29. As a 内容核验者, I want DOCX 的段落和表格都能按所声明的正文块计数规则定位, so that 表格位置不会误写成段落号或页码。
30. As a 内容核验者, I want 来源信息与实际输出内容对应, so that 不会用文档总页数冒充某段正文所在页。
31. As a 调用方, I want 无法读取、格式不支持或文件损坏时得到明确失败, so that 不会把错误提示当作成功正文。
32. As a 调用方, I want 整份文档没有可用正文时得到明确结果, so that 空字符串或图片占位不会冒充取得了目标文字。
33. As a 内容核验者, I want 已知解析损失与技术局限单独记录, so that 能够判断下一步应检查哪一层。
34. As a 测试维护者, I want 通过公开入口运行真实解析实现, so that 测试能够反映实际调用行为。
35. As a 测试维护者, I want 使用固定输入及已知维护规则和设备周期关系验收, so that 检查不限于输出非空或没有异常。
36. As a 测试维护者, I want 保留历史 OCR 失败样本及其实际结果, so that 不会把调用成功误记为识别质量通过。
37. As a 测试维护者, I want 记录输入版本、处理路径、依赖版本及运行观察, so that 实验结论可以复核。
38. As a 学习者, I want 解析业务代码集中在指定子模块且有清楚的入口说明, so that 笔记知识点能够直接对应到实现职责。
39. As a 下游模块开发者, I want 本模块完成解析后交付整篇正文及来源关联, so that 最终切块、检索与问答仍由各自模块负责。

## Implementation Decisions

- 本期实现范围为文档入库与解析中的 PDF 与 Word 解析子模块。解析业务入口、PDF 处理、DOCX 处理、OCR 衔接以及本模块需要的结果表达集中在用户指定的子模块内，不为本篇补齐空的上传服务、格式总路由或切块模块。
- 首版处理 PDF 与 DOCX；“Word”在本规格中指实际复习与实验覆盖的 DOCX，不据此宣称支持旧版二进制 Word 文件。
- 沿用邻近文本与网页模块的使用约定：接受本地文件或已有字节；字节入口显式取得格式和来源；输出整篇 Markdown 正文；来源、警告和失败原因独立于正文。失败结果不提供可被当作成功正文的错误字符串。
- 公开解析入口是主要调用和测试边界，文件读取与内容转换可复用同一内部流程。具体函数命名和结果类型由实现按仓库现有风格确定，不要求为本篇先建立跨模块通用框架。
- 外部输入只在公共入口完成必要校验；内部使用已确定类型的值，避免重复防御性检查和仅为假想扩展增加的抽象。
- PDF 按页提取，并将页面内容与实际 PDF 页序关联。有质量可用的文本层时优先利用文本层；扫描页走实际渲染和识字路径。文本非空只能作为观察信号，不构成质量正确、标题完整或表格关系保留的证明。
- 已有文本层的页面不必统一重做 OCR；统一 OCR 可以是一种替代处理方式，但本期不为此另建多引擎比较平台。路径选择需考虑计算开销与识别误差。
- OCR 衔接必须有实际执行能力，不能仅返回页面图片引用、图片占位或空扩展点。使用实际可用的识字路径；具体渲染库、识字引擎和版本在实现时选择并记录，不把历史 Windows OCR 或任何尚未运行的候选方案当作已确定成功方案。
- 识字、阅读顺序恢复和表格关系恢复是不同职责。输出 OCR 文字或词框不能直接宣称已经完成表格结构恢复；扫描表格仅有平铺词语时应记录关系未恢复，不能通过表格关系验收。
- 本期保留可用正文及必要结构，不承诺任意 PDF 的标题层级、双栏、跨页表格或复杂版面均能自动正确恢复。对代表样本核验实际效果，对已知损失明确说明，不通过改大切块或依赖模型猜测掩盖上游损失。
- DOCX 按正文中的结构顺序遍历标题、段落与表格，转换时保留标题层级、表格在正文中的位置及普通表格对应关系。不采用先输出所有段落再追加所有表格的转换行为。
- 普通表格可表示为保留表头与行列的 Markdown 表格，或具有同等明确关系的结构化文本；验收依据是对象、属性和值的对应，而非单纯词语覆盖。
- 选择同版本完整 DOCX 是调用方对输入材料的判断前提，本期不实现跨文件自动比对版本、完整性检查或 PDF 与 DOCX 的自动优选系统。
- 除整篇 Markdown 外，保留足以将内容对应回实际页面或正文块的来源信息。无需预先锁定具体字段布局，但不能只记录文档名或总页数后宣称内容已经定位。
- PDF 记录实际 PDF 页序，区分页序与页面印刷页码；没有实际映射时不生成印刷页码。
- DOCX 没有可靠页码时使用文档、章节和正文块位置。计数规则需明确段落、表格及标题是否参与、何时重置，保持实现、说明与测试一致；章节内第 2 个正文块不等于第 2 页。
- 如保留 OCR 词框，应明确其坐标属于送入识字引擎的图片及相应渲染比例。未经映射不标为原 PDF 坐标；不为本期额外建设坐标还原系统。
- 读取失败、不支持格式、损坏文件、OCR 运行不可用或执行失败、整篇没有可用正文等情况应有明确诊断。页面处理问题需能定位，不能静默省略失败页面并伪装为整篇处理完整。
- 技术执行结果与内容质量核验分开：解析器可以报告实际执行状态和已知问题；关键规则是否识别正确由原文对照和固定样本验收判断，不要求通用解析器自动理解并校正所有业务事实。
- 依赖沿用项目现有的集中声明与安装流程。历史实验使用过的库可作为实现参考，不能以全局 Python 已安装某个库代替项目环境中的依赖声明和验证。
- 本期不引入新的服务、队列、数据库、测试平台或长期难以更换的架构约束；没有需要单独记录为 ADR 的已确定架构取舍。

## Testing Decisions

- 用户已确认以本模块公开解析入口作为主要验收边界：输入真实 PDF 或 DOCX，检查整篇 Markdown 正文、阅读顺序、标题、表格对应关系、来源信息和失败结果。以最高可用行为边界覆盖内部组合，不绑定内部辅助函数或调用次数。
- 测试运行真实读取、解析和转换实现，尽量少用 mock；OCR 验收至少包含一条真实识字路径。模拟结果不能作为 OCR 质量或扫描表格恢复成功的证据。
- 沿用仓库标准库 unittest 及现有测试组织方式。现有文本与网页模块已经通过公开文件和字节入口检查正文、来源、诊断隔离、表格和失败行为；复用这一风格，不复制业务解析算法到测试中。
- 自动测试与固定输入沿用仓库现有测试和样本目录，不将测试平台塞入业务模块。新增样本核对 Git 收录状态；已存在的样本忽略规则不能使验收依赖无法分享的本地文件。
- 优先复用笔记已有的数字 PDF、扫描 PDF、表格 DOCX 教学样本，以原始字节、摘要和已知事实记录身份。只在覆盖明确行为所必需时补充混合 PDF、多个设备周期、标题层级或失败输入，不在本次规格整理阶段把未准备的样本写成已有材料。
- 数字 PDF 检查已知标题、断电规则、检查周期及实际页序关联，不只断言结果非空。不把单页样本通过推广为任意复杂 PDF 无损。
- 混合 PDF 使用同时含可用文本页和纯扫描页的固定样本，通过公开入口检查两类内容均进入正文，并且页序和来源没有串页。不靠内部调用次数证明路径效果。
- DOCX 检查“标题 → 断电说明 → 设备周期表 → 重新启动说明”的原始顺序；表格仍位于两段说明之间，标题层级与章节归属可检查。
- 表格至少核对设备、周期及其对应关系；补充“泵—每月、阀门—每季度”时分别验证两组关系，防止只测全部词语是否出现。
- 扫描 PDF 分开记录文本层直接提取与实际识字结果，核验维护规则的完整性。图片引用、识字调用完成或输出非空均不能单独通过正文质量验收。
- OCR 关键内容核验关注否定词、数字、单位和表格对应关系。历史漏字结果保留为失败观察；实现更换路径后必须重新运行并对照原文，不能把方案设计写成已经修复。
- 扫描表格检查实际输出是否保留表头与行列对应；仅有设备和周期的平铺词语时记录表格关系未恢复，不能按表格解析成功记账。复杂结构不支持的局限与实际执行失败分开说明。
- 来源核验检查 PDF 内容对应的实际页序、DOCX 章节与正文块位置，以及计数规则。没有可靠页码时不出现推估的 Word 页码；总页数不能充当正文位置。
- 如输出 OCR 词框，检查其坐标空间说明与实际输入图片一致；不把词框存在当作原 PDF 坐标或表格结构恢复的证明。
- 失败验证覆盖读取失败、格式不支持、文件损坏、实际 OCR 不可用或失败、整篇无正文等可观察行为。来源和诊断不混入 Markdown 正文，失败不返回冒充成功的错误正文。
- 有 OCR 环境限制时明确记录未运行原因和未覆盖项；跳过识字验证不等于扫描路径通过。实现验收需要给出至少一条实际识字运行的结果和局限。
- 实验记录包含固定输入及版本、采用路径和依赖、预期与实际、失败、耗时观察及局限；只有实际测量才报告时间或优化效果，不编造准确率和提升比例。
- 本模块通过只证明声明样本和行为的解析检查成立，不等于上传、索引、召回、模型输入、回答或引用等完整 RAG 链路验证完成。

## Out of Scope

- 旧版二进制 Word 格式、PPT、表格文件、音视频、ZIP 等其他载体。
- URL 下载、爬虫、上传 API、摄取服务、格式总路由、队列、存储、数据库及尚为空的统一交接模块建设。
- 最终文档切块、token 预算、embedding、索引、检索、模型问答、答案正确性和引用链路的完整系统验收。
- 跨文件自动核对版本与完整性、自动选择 DOCX 或 PDF、DOCX 到 PDF 页码的映射。
- PDF 底层排版研究、OCR 模型内部、训练或微调、自建通用版面或表格识别平台。
- 任意复杂双栏、合并单元格、跨页表格及复杂扫描表格的无损恢复承诺；OCR 图像坐标到原 PDF 坐标的完整还原。
- 要求用户阅读参考项目源码，或复制参考项目的完整解析与服务架构。
- 多 OCR 引擎、云服务或视觉模型的全面比较，以及没有实际数据支持的通用质量保证。
- 为假想竞态、安全边界或未来格式扩展增加与本篇目标无关的复杂度。
