# 统一输出与切分交接：保留正文、结构、来源和处理状态

> 规格：[GitHub Issue #45](https://github.com/yb2915722928-cpu/rag_me/issues/45)。任务：#46–#51。

## Problem Statement

现有各类解析器已经能返回 Markdown 正文或图片、媒体派生文字，但结果形态不同：文档有正文区间，表格有行列与单元格，演示文稿有演示页及对象，结构化文档有节点路径，音视频有片段时间，ZIP 有独立成员。下游如果只取正文，会丢失条件归属、来源和待核验信息；如果强制补成同一粒度，又会制造原资料没有的位置。

用户需要将笔记中“内容及其关系的交接”落实为可运行模块，为后续文档切分提供一致入口。扩大切块只能容纳已提取的内容，不能修复上游已经遗漏的条件；本节必须让这一边界可观察。

## Solution

增加单向交接适配：接收现有解析器已经生成的结果，输出包含独立文档、内容单元、结构关系、真实来源与诊断的统一结果，并支持 UTF-8 JSON 导出。覆盖文本与网页、PDF/DOCX、CSV/XLSX、PPTX、JSON/XML、图片、音视频及 ZIP 成员。

保留原正文及其表示方式。已有精确对应的位置继续对应原正文；只有文档、节点、服务块或片段级来源时保留该实际粒度，并明确对齐限制。失败、没有派生文字、无法确认关系、待核验与 ZIP 部分成功分别表达。本节不运行切块算法，也不重新调用解析器或云端模型。

## User Stories

1. As a 知识库开发者, I want 通过同一交接入口消费现有解析结果, so that 后续切分无需直接依赖每类解析器的结果类型。
2. As a 调用方, I want 保留解析器输出的完整正文, so that 交接不会删改原本已提取的必要条件。
3. As a 调用方, I want 区分 Markdown 正文和普通派生文字, so that 下游不会错误解释正文格式。
4. As a 调用方, I want 整篇文本也能交接, so that 没有正文块信息的短公告不必虚构章节。
5. As a 内容核验者, I want 每个内容单元关联真实来源, so that 文件名和位置不会变成无法对应正文的孤立列表。
6. As a 内容核验者, I want 已知业务文档标识和版本可显式传入, so that 同一业务资料的版本能够被区分。
7. As a 内容核验者, I want 未知业务标识和版本明确为空, so that 文件名、条目序号或字节摘要不会被误认为业务版本。
8. As a 下游开发者, I want 单次交接中的文档和内容单元有唯一标识, so that 关系和诊断可以明确引用对应对象。
9. As a 下游开发者, I want 知道这些标识只在当前结果内有效, so that 不会误作跨次解析的稳定业务标识。
10. As a 文本使用者, I want 保留来源位置、编码和实际选中的 MHTML 部分, so that 能核查本次正文来自哪里。
11. As a PDF 使用者, I want 保留实际 PDF 页序和提取方式, so that 可以区分本地文本与 OCR 来源。
12. As a DOCX 使用者, I want 保留章节、正文块类型及顺序, so that 条款与所属章节不会脱离。
13. As a 内容核验者, I want 正文字符区间保持原有半开区间含义, so that 可用原正文切片验证对应内容。
14. As a 托管文档使用者, I want 服务结构及其真实来源完整保留, so that API 结果的阅读顺序和位置限制可以继续检查。
15. As a 托管文档使用者, I want 未建立字符映射的结构块明确标记限制, so that 不会把服务块序号当成精确正文定位。
16. As a Office 使用者, I want 服务页序与原生单元格或演示对象位置区别表达, so that 不会产生虚假页码或坐标。
17. As a 表格使用者, I want 保留完整列名和表格共同上下文, so that 数据行中的值仍能按对象、单位与条件解释。
18. As a 表格使用者, I want 保留行、列、单元格及真实位置, so that 同名值不会失去归属。
19. As a 表格使用者, I want 按行表示连同对应上下文交接, so that 不依赖整表正文也能理解一条记录。
20. As a 表格使用者, I want 公式、缓存、显示值和原始值分别保留, so that 导出不会把历史缓存冒充实时计算。
21. As a 演示文稿使用者, I want 保留原演示页、对象及备注归属, so that 不同页的条件与结论不会混合。
22. As a 内容核验者, I want 非文本演示对象仍保留来源和待核验信息, so that 没有派生正文不被误作对象不存在。
23. As a 结构化文档使用者, I want 保留节点类型、节点路径及父路径, so that 数组成员和同名元素保持可区分。
24. As a 结构化文档使用者, I want 节点路径不被转成猜测的字符偏移, so that 原结构定位的含义不被夸大。
25. As a 图片使用者, I want 区分识字、图像描述和视觉理解, so that 画面解释不会冒充原文。
26. As a 图片使用者, I want 保留图片版本标识及已有原图映射, so that 可以回到实际使用的图片证据。
27. As a 图片使用者, I want 无文字、无法确认与调用失败分别保留, so that 空正文不会掩盖真实处理状态。
28. As a 音视频使用者, I want 区分语音与画面派生文字, so that 模型解释不会被当成说话原文。
29. As a 音视频使用者, I want 保留实际片段起止时间及精度, so that 下游可以回听回看且不夸大到逐词定位。
30. As a 音视频使用者, I want 保留未知说话人及原媒体版本, so that 不会猜补身份或混用同名文件。
31. As a 内容核验者, I want 模型、提示词、问题及待核验信息随内容保留, so that 生成内容的用途和局限可以继续判断。
32. As a ZIP 使用者, I want 每个成功成员独立交接, so that 资料包不会被拼成一篇丢失边界的正文。
33. As a ZIP 使用者, I want 同名成员用原条目序号区分, so that 不会覆盖归档中的不同资料。
34. As a ZIP 使用者, I want 失败、忽略及未处理成员仍出现在报告中, so that 资料集合的不完整可见。
35. As a ZIP 使用者, I want 部分成功保留可用内容及整包状态, so that 下游不会把成功子集当成资料包全部处理完成。
36. As a 调用方, I want JSON 导出保留中文、空值及全部来源关系, so that 结果可检查、保存和交给后续模块。
37. As a 调用方, I want 表格中的日期等原生值有明确的 JSON 表示, so that 含非字符串值的真实表格也能交接。
38. As a 内容核验者, I want 技术处理完成与内容已核验分别表达, so that 交接成功不会升级为质量通过。
39. As a 维护者, I want 通过现有解析器和固定样本验证交接, so that 测试反映真实输入输出而不是复制业务逻辑。
40. As a 维护者, I want 交接层不再次解析或调用模型, so that 来源、处理路线及费用不会被悄然改变。

## Implementation Decisions

- 增加独立的统一输出与切分交接模块，接收现有第2–8节公开原生结果；不建立统一文件或字节解析总路由。
- 采用一份交接报告承载独立文档；ZIP 另保留成员清单和整包信息。每份文档保留原正文、表示方式、内容单元、结构来源与诊断。
- 业务标识与版本由调用方在已知时显式提供，未知保持空。单次结果内部标识由适配层分配，只保证内部引用唯一；ZIP 容器标识与成员文档标识不能混为一谈。
- 文本与网页保留整篇正文；不靠重新识别 Markdown、模型补全或搜索文本匹配猜测原始章节和位置。
- PDF/DOCX 及 PPTX 中实际给出的正文区间按原正文解释。没有来源覆盖的正文仍保留，不因生成内容单元而丢失标记或文本。
- 表格交接使用上游已经生成的按行文字，并保留完整表、列、行、单元格、共同上下文和原位置；不重算公式，也不把这些位置伪装成正文字符区间。
- JSON/XML 保留完整原正文及原生节点父子来源。节点定位独立于正文字符位置，不从字符串匹配推测对齐。
- 托管文档保留原 Markdown、结构产物及来源；不能精确对应的结构与正文分别明确表达，沿用上游对阅读顺序、表格关系和页序的限制。
- 图片保留任务、状态、问题、生成信息、图片版本及原图映射。媒体按上游片段保留语音／画面种类、实际时间与精度、状态和未知说话人。
- 诊断、错误、待核验事项与正文分别承载；失败不制造可交接正文，正常空内容和不确定结果不升级为失败或已核验。
- ZIP 每个成员保持独立，保留容器、原路径、条目序号、成员状态及错误。整包部分成功保留，上游失败或未处理不能被过滤掉。
- 公开适配入口只接受明确支持的结果类型，并校验新增的业务参数；内部沿用已经确定的上游类型，不重复做防御性校验。
- 结构化 JSON 使用 UTF-8，日期／时间类值使用明确的 ISO 文本表示，其他既有 JSON 标量保持原类型。导出包含失败与不完整报告，便于诊断；该行为区别于仅导出成功正文的旧接口。
- 沿用现有 ZIP API 优先架构决策，不引入新依赖、供应商、存储或本地模型，不为理论边界情况扩展平台能力。

## Testing Decisions

- 主要测试边界为公开交接入口及 JSON 导出，测试外部可观察的内容、归属、来源和状态，不测试私有函数结构或复制业务转换逻辑。
- 复用现有文件和字节解析入口及固定样本作为真实输入；延续已有双入口契约、ZIP 跨格式投影及来源保留测试的方式。
- 核验售后条件、表格列值、章节归属、页序、节点父子关系和媒体时间等具体证据，不能仅断言正文非空。
- 对真实正文区间验证切片相等，对未提供对齐的结构验证其位置保持空且限制可见；检查没有来源覆盖的正文未丢失。
- 覆盖成功、失败、无文字、无法确认、待核验、ZIP 部分成功及同名条目。核验技术完成不等于质量通过。
- 核验 JSON 回读保留关系、中文、空值、日期类值，以及不同结果类型的处理状态；验证调用前后原生输入结果不被修改。
- 托管文档和多模态用现有本地 HTTP 服务生成原生输入，再执行纯适配；不为本次交接重复运行云端质量验收。
- 完成新增契约测试后运行仓库现有 unittest 回归；不新增测试框架。当前后续切块模块尚空，验收边界明确止于交给它的内容与关系。

## Out of Scope

- 实际切块算法、chunk 长度、重叠、token 预算、策略比较及效果优化。
- 修复上游解析遗漏、语义补全、重新读取原文件或模型猜补缺失信息。
- 逐词时间、OCR 字框、精确引用高亮及不存在的跨表示字符映射。
- 跨次解析的稳定块标识、业务文档生命周期、去重、持久化及版本管理服务。
- 新解析器、总格式路由、文件抓取、统一上传 API、数据库、前端及任务平台。
- embedding、索引、召回、完整问答链路和模型输出质量保证。

## Further Notes

- 需求来自用户提供的“统一输出与切分交接”学习笔记；笔记中的售后条款为教学样例，不能当成本项目已验证结果。
- 用户已确认本节只负责交接、覆盖现有全部结果、接收原生解析结果并导出 JSON。
- 参考 [Unstructured 官方切分说明](https://docs.unstructured.io/api-reference/legacy-api/partition/chunking)中“使用已有文档元素及元数据组织内容”的职责边界；本项目只做最小适配，不引入其库或切分策略。
- 现有 ZIP API 优先架构约束继续有效，尤其是服务位置与原生来源粒度不能互相冒充。
- 测试入口与任务拆分已获用户确认。规格与六个子任务已发布，后续由用户调用 implement-spec 授权实施。
